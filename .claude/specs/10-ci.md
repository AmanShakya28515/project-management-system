# 10 — Continuous integration

## Goal
Every push to GitHub automatically runs the project's verification (the
migration-drift check, the system check and the full test suite), and
GitHub shows a clear pass or fail for each commit.

## Context / why now
- Step 08 put the project under Git, and the repository is now on GitHub
  (`main` was pushed after step 09).
- Step 09 runs the app on PostgreSQL in Compose, while the host `.venv`
  stays on SQLite. Today both are verified only by hand, on one machine.
- CI is the next DevOps stage in CLAUDE.md, after Docker and PostgreSQL.
  Later deployment steps will rely on it: only code that passed CI gets
  deployed.
- Step 08's Q-74 (the floating `python:3.12-slim` tag) was deferred to
  "the CI/CD step" for reproducible builds.

CLAUDE.md's rules still apply and aren't repeated here: the dev-only
labelled values, no real secrets in tracked files, Claude commits and
pushes only when asked.

## User stories
- As a developer, I want every push tested automatically, so that a
  broken change is caught even when I forget to run the suite.
- As a learner, I want to see a pipeline run the same checks I run
  locally, so that I understand what CI does before deployment steps
  build on it.

## Acceptance criteria

### Triggers and result
- **AC-1** Given a push to any branch of the GitHub repository, then a CI
  run starts automatically, with no manual action (see OQ-3).
- **AC-2** Given a pull request into `main`, then a CI run starts for it
  and its result shows on the pull request (see OQ-3).
- **AC-3** Given a CI run, then its result is shown on the commit in
  GitHub as passed or failed, and its log shows each check's output.

### What the run checks
- **AC-4** Given a CI run, then it runs, in CLAUDE.md's standard order:
  the migration-drift check, the system check and the full test suite.
  A later check runs only if the earlier ones passed.
- **AC-5** Given a CI run, then the suite runs against **PostgreSQL 17**,
  the same major version as Compose, and against **SQLite**, as the host
  workflow does (see OQ-2). Both must pass for the run to pass.
- **AC-6** Given a CI run, then it uses Python 3.12 and installs
  dependencies from `requirements.txt` only, with no extra packages.
- **AC-7** Given a CI run, then the development Docker image builds from
  the project's `Dockerfile` (see OQ-2).

### Failure behaviour
- **AC-8** Given a change that breaks a test, a check or the migration
  state, when it's pushed, then the run fails and the log names the
  failing check. This is demonstrated once, on a throwaway branch that is
  deleted afterwards, and never on `main`.
- **AC-9** Given the current code, then the run on `main` passes, with
  all 411 tests on each database.

### Safety and reproducibility
- **AC-10** Given the CI configuration, then it needs no repository
  secret and contains no real credential. Any database values are
  development-only and labelled so, and the CI database isn't reachable
  from outside the run.
- **AC-11** Given the CI configuration, then every external building
  block it uses (pipeline actions, container images) is pinned to a
  version, so a run doesn't silently change because something upstream
  did (see OQ-4).
- **AC-12** Given the finished step, then the application, its tests and
  the local `.venv` and Compose workflows are unchanged, apart from any
  version pin agreed in OQ-4.

### Documentation
- **AC-13** Given the documentation:
  - `README.md` explains where to see CI results, what a run checks and
    how to reproduce a failure locally;
  - it explains in plain language: CI, a workflow, a trigger, a job and a
    step, a runner, a service container, why both databases are tested,
    and why versions are pinned;
  - `CLAUDE.md` records the lasting decisions.

## Out of scope
- Deployment or continuous delivery of any kind; publishing images to a
  registry
- Linters, formatters, type checkers, coverage reports, security scanners
  (each needs its own approved step, per CLAUDE.md)
- A production image, Gunicorn, HTTPS or production settings (S-2)
- A dependency lock file; `requirements.txt` keeps its `~=` ranges
- Branch protection rules on GitHub (a repository setting you can turn on
  yourself; the README may mention it)
- Moving credentials out of `compose.yaml` (Q-78)
- Any change to application features or tests

## Open questions
Each has a proposed answer, and the ACs assume it. **All five were
accepted as proposed when the spec was approved on 2026-10-27.**

- **OQ-1 CI platform.** *Proposed:* **GitHub Actions**. The repository is
  already on GitHub, it needs no extra account or server, and the
  configuration lives in the repository. Private repositories get a free
  monthly allowance of minutes, and a run of this size uses only a few.
  → all ACs
- **OQ-2 How the two databases are tested.**
  - *Proposed:* two independent jobs that run in parallel.
    - **PostgreSQL job:** builds the project's development image and runs
      the checks and suite through Docker Compose, as you do locally. It
      tests the real Compose setup, and proves the image builds (AC-7).
    - **SQLite job:** Python 3.12 directly on the runner, as in the host
      `.venv` workflow.
  - *Alternative:* one job, Python 3.12 on the runner with a PostgreSQL
    service container, and no Compose. Faster, but it doesn't test the
    image or the Compose file you actually use.
  - *Alternative:* PostgreSQL only. Simpler, but the SQLite workflow
    could break unnoticed. → AC-5, AC-7
- **OQ-3 Triggers.** *Proposed:* every push to any branch, plus pull
  requests into `main`. Runs for an older commit on the same branch are
  cancelled when a newer one is pushed, to save minutes. → AC-1, AC-2
- **OQ-4 Pinning (settles Q-74).**
  - *Proposed:*
    - pipeline actions pinned to a major version tag;
    - the `Dockerfile`'s Python image pinned to an exact patch-version
      tag (e.g. a `3.12.x-slim` tag), for local and CI builds alike;
    - `postgres:17` pinned to an exact minor version in `compose.yaml`.
  - Updating a pin then becomes a small, deliberate change.
  - *Not proposed now:* pinning to image digests or action commit hashes.
    It's stronger but needs an update process (e.g. Dependabot), which
    would be its own step. → AC-11, AC-12
- **OQ-5 Dependency versions in CI.** *Proposed:* accept that CI, like a
  fresh local install, gets the newest release inside each `~=` range. A
  new patch release could therefore change a run's result without a code
  change. A lock file is out of scope. → AC-6
