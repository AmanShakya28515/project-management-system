# Plan 10 — Continuous integration

## Approach
- One GitHub Actions workflow, `.github/workflows/ci.yml`, with two
  independent jobs that run in parallel (OQ-2). The run passes only when
  both pass (AC-5).
  - **`postgres`:** builds the development image and runs the three checks
    with `docker compose run --rm web …`. `run` starts `db`, waits for its
    TCP health check (`depends_on: service_healthy`, step 09), and runs one
    command in a fresh `web` container. It doesn't start `runserver` or
    publish port 8000. This tests the real `Dockerfile` and `compose.yaml`
    (AC-7), and `db` stays unreachable from outside the run (AC-10).
  - **`sqlite`:** `actions/setup-python` with Python 3.12, `pip install -r
    requirements.txt`, then the same three checks, with no `DJANGO_DB_*`
    set, so settings choose SQLite exactly as in the host `.venv`.
- **Each check is its own step**, in CLAUDE.md's order: drift, then
  `check`, then `test`. A failed step stops its job, so later checks only
  run after earlier ones pass, and the log names the failing step
  (AC-4, AC-8).
- **Triggers (OQ-3):** `push` on every branch (`branches: ['**']`, which
  leaves out tags) and `pull_request` into `main`. A `concurrency` group
  per ref, with `cancel-in-progress: true`, cancels an older run on the
  same branch.
- **Least privilege:** `permissions: contents: read`. The workflow uses no
  secrets; the only database values are the dev-only ones already in
  `compose.yaml` (AC-10).
- **A time limit per job** (`timeout-minutes: 15`), so a hang can't run for
  hours. A normal run takes a few minutes (the suite took 83 s on
  PostgreSQL locally).
- **Pins (OQ-4, settles Q-74):** the runner image (`ubuntu-24.04`, not
  `ubuntu-latest`), actions at their current major tag, the Python and
  PostgreSQL images at exact versions (D-1).

**Why `docker compose run` and not `up` + `exec`:** `up` starts
`runserver` and needs a wait for `web` too; `run` gives one clean
container per check and its exit code becomes the step's result.

**Why `--noinput` on `test` in CI only:** if a stale test database ever
exists, Django asks a question and a non-interactive run would hang until
the time limit. CI never has a stale one, so it doesn't change results.

**Visibility:** the repository is public (the GitHub API answers without a
token), so Actions minutes are free, and `/build` can read run results
from the public API with `curl` (no `gh` CLI installed, none needed).

## Risks
- **A push and a pull request run the same commit twice.** Accepted:
  public-repo minutes are free, and the two show in different places.
- **The bind mount in CI:** `compose.yaml` mounts the checkout at `/app`,
  over the image's copy. In CI they're the same files, so it's harmless,
  and it keeps the CI run identical to local use.
- **Pinned images get no security patches automatically.** That's the
  trade-off OQ-4 chose; updating a pin is a one-line change. Automated
  updates (Dependabot) would be their own step.
- **Changing the Debian base could change glibc's case tables**, which
  `LOWER()` relies on (step 09 D-3). D-1 pins the Debian release that is
  already in use, so nothing changes now.
- **Public repository:** the workflow and logs are public. They hold only
  the dev-only values already public in `compose.yaml`. No secrets are
  used, and pull requests from forks get read-only tokens by default.
- **The throwaway branches** run the workflow on GitHub. They're deleted
  afterwards and never merged.

## Decisions needing approval
_All three (D-1 to D-3) accepted as proposed with plan approval, 2026-10-27._

- **D-1 — Image pins include the Debian release.** OQ-4 asked for exact
  version tags. A tag like `3.12.x-slim` can still move to a newer Debian
  release, so `/build` pins the `-<debian>` variant too (for example
  `python:3.12.x-slim-trixie`, `postgres:17.x-trixie`), using the release
  each image already uses today. It's stricter than the spec's example,
  but within its aim.
- **D-2 — Pin the runner image** to `ubuntu-24.04` rather than
  `ubuntu-latest`. It's an external building block under AC-11.
- **D-3 — Outward-facing actions.** Steps 7–9 push to GitHub (one commit
  on `main`, one throwaway branch, possibly one throwaway pull request).
  `/build` stops before each and asks you.
